# Version 3.17 #

## guidata Version 3.17.3 ##

🛠 Bug fixes:

* **Unreadable histogram range parameters** — text and HTML representations of datasets containing a histogram range editor (e.g. DataLab's **Brightness and contrast** parameters) showed the complete histogram instead of the selected range. They now show the bounds using their display formats, consistently before and after saving the parameters (fixes [Issue #149](https://github.com/PlotPyStack/guidata/issues/149)).
* **Truncated and unreadable range fields** — the Minimum and Maximum fields of the histogram range editor (`HistogramRangeItem`, e.g. the **Brightness and contrast** processing of DataLab) showed 17 significant digits in a field too narrow for them, so that the beginning of the values was cut off (e.g. `835736228608e-43` instead of `6.5127532828723551e-44`). The bounds are now shown with the precision of the range sliders (e.g. `0` and `1.7557` for a range from 0 to 1.76), with their exact value in the tooltip, and the fields are sized from the font to show these values entirely. The exact bounds are kept as long as a field is not modified: validating a field without changing it no longer replaces the bound with its rounded value (fixes [Issue #152](https://github.com/PlotPyStack/guidata/issues/152)).
* **Slider values with binary noise** — moving the slider of a floating point item gave values such as `0.30000000000000004` or `-0.8200000000000001` instead of `0.3` or `-0.82`, which were shown and stored as is. This occurred with the sliders added to bounded items by `DataSetEditLayout(..., auto_sliders=True)` (e.g. in the processing parameters of DataLab), and with the sliders of items created with `slider=True` for some bounds. Slider values are now free of this noise, and remain within the bounds of the item (fixes [Issue #152](https://github.com/PlotPyStack/guidata/issues/152)).
* **JSON Schema export failing with dynamic bounds** — exporting a dataset to JSON Schema (`dataset_to_schema`, e.g. to build a web form) gave a schema that could not be serialized to JSON when a numeric item had a dynamic bound (e.g. `set_prop("data", min=GetAttrProp("lower"))`), and marked items with a dynamic read-only state (e.g. `set_prop("display", readonly=GetAttrProp("locked"))`) as always read-only. Dynamic bounds and read-only states are now left out of the schema, which only contains static ones (fixes [Issue #124](https://github.com/PlotPyStack/guidata/issues/124)).

## guidata Version 3.17.2 ##

🛠 Bug fixes:

* **Light theme remaining dark** — with Qt 6.7 or later on Windows 11 in dark mode (or with a dark desktop theme on Linux), selecting the light color mode (`set_color_mode("light")`, e.g. in the settings of PlotPy or DataLab) kept a dark interface, slightly different from the dark theme: Qt 6 now derives its default palette from the system color scheme, and this dark palette was restored for the light theme. With Qt 6.8 or later, the color mode is now applied by Qt itself, whatever the system color scheme: the light and dark themes use Qt's official styles and palettes (e.g. the native "windows11" style on Windows 11, or the Fusion style when the default style does not support the dark color scheme, like "windowsvista" on Windows 10). With earlier Qt versions or on platforms where Qt can't apply the color mode, guidata's dark theme is unchanged, and the light theme uses Qt's default light palette when the system palette is dark (fixes [Issue #139](https://github.com/PlotPyStack/guidata/issues/139)).
* **Toolbar overflow button drawn for the previous theme** — after switching between the light and dark themes, the button shown when a toolbar overflows (`»` or `···`) kept its icon drawn for the previous theme, so that it was hardly visible. Its icon is now drawn again for the new theme. With the dark theme applied natively with the Fusion style, this icon (a fixed dark image with this style) is drawn with the text color of the theme, so that it remains visible (fixes [Issue #139](https://github.com/PlotPyStack/guidata/issues/139)).
* **White separator lines in the dark theme** — with guidata's dark theme (used with Qt 5, or when Qt can't apply the dark color mode itself), separator lines (e.g. between the methods of the DataLab Applications panel) and other sunken or raised frames were drawn in white, much too contrasted on the dark background: the palette kept the relief colors of the light system palette. These colors now follow the dark theme, as in the dark palette of Qt's Fusion style (fixes [Issue #141](https://github.com/PlotPyStack/guidata/issues/141)).
* **Light theme turning dark when the system switches to dark** — with Qt 6.5 to 6.7 (e.g. on Windows 11 or on a Linux desktop), when the system color scheme switched to dark while the application was running with the light theme, the whole interface turned dark (palette, controls and title bars), as if the dark theme had been selected: the light theme restored the default palette, which follows the system color scheme. The light theme is now applied again when the system color scheme changes, and remains light: with Qt's default light palette and the Fusion style while the system color scheme is dark, and with the default style and palette while it is light (fixes [Issue #147](https://github.com/PlotPyStack/guidata/issues/147)).
* **White title bars in the dark theme on Windows** — with the dark theme on Windows, most windows kept a white title bar: only the windows of guidata and PlotPy (and those of applications calling `win32_fix_title_bar_background`) had a dark one. The other dialogs of applications, the message boxes and input dialogs created by static methods (e.g. `QMessageBox.warning`, `QInputDialog.getText`), the floating dock widgets, and the windows created again (e.g. after `setWindowFlags`) remained white. Once the color mode has been set (`set_color_mode`, called when the application is created with `guidata.qapplication` or `qt_app_context`), the title bar of every window now follows the color theme when the window is created and when the color mode changes, including when switching from the light theme to the dark one with Qt 6.5-6.7 and a light system color scheme (Qt set the title bar of the existing windows light again). With Qt 6.8 or later, when the color mode is applied natively by Qt, the title bars are left to Qt, which gives them the color theme. Windows without a title bar (menus, tooltips, splash screens) are left untouched, and `win32_fix_title_bar_background` (still available for applications creating their own `QApplication`) no longer creates the native window of the widget early. The title bar is set with the documented Windows function used by Qt 6 (fixes [Issue #143](https://github.com/PlotPyStack/guidata/issues/143)).

## guidata Version 3.17.1 ##

🛠 Bug fixes:

* **Blurry icons with display scaling** — the icons provided by guidata (array, dictionary and DataFrame editors, console, file types, ...) were 16×16 pixel PNG images, which looked blurry with a display scaling greater than 100% (e.g. 125%, 150%, 200%). They are now SVG images, which remain sharp at any display scaling. `get_pixmap` (and thus `get_image_label` and `get_image_layout`) renders SVG images at the resolution of the display. Applications requesting an icon by its former PNG name (e.g. `get_icon("apply.png")`) still get it: when a `.png` image is not found, the `.svg` image with the same name is used. The notices of the original artwork are provided in `guidata/data/icons/LICENSES.txt` (fixes [Issue #129](https://github.com/PlotPyStack/guidata/issues/129)).
* **Application icons hidden by library icons with the same name** — since library icons are SVG images, they share their names with the SVG icons of applications (e.g. `apply.svg`, `delete.svg`, `edit.svg`): as libraries register their image paths before applications, their icons silently replaced the application icons with the same name. The image paths registered last are now searched first, so that the icons of an application take precedence over those of the libraries it depends on. When several image files match a name, an `ImageNameConflictWarning` lists them, and the new `"module:filename"` syntax (e.g. `get_icon("guidata:apply.svg")`) designates an image explicitly among those registered for a module with `add_image_module_path`; if the image is not found there, the part after the colon is taken as a path relative to the directory of the module's package (`"package:path"` syntax, e.g. `"my_plugin:icons/logo.svg"`, as used by DataLab plugins). guidata designates its own ambiguous icons explicitly (fixes [Issue #131](https://github.com/PlotPyStack/guidata/issues/131) and [Issue #133](https://github.com/PlotPyStack/guidata/issues/133)).
* **Blurry standard icons with display scaling** — `get_std_icon(name, size)` froze the standard Qt icon to a single pixmap rendered for `size` pixels, so that the icon was upscaled, and blurry, when shown larger or with a display scaling greater than 100% (e.g. in PlotPy toolbars). The `size` argument is now deprecated and ignored (`DeprecationWarning`): the icon keeps all its resolutions, and the widget showing it sets its display size. The "Browse..." button of directory items now shows guidata's SVG folder icon: the standard folder icon only exists at 16 pixels on Windows (fixes [Issue #135](https://github.com/PlotPyStack/guidata/issues/135)).
* **Blurry low-resolution standard icons** — some standard Qt icons are only provided at low resolution by the platform (on Windows: 16 pixels for the folder icons, 32 pixels for the information, warning and error icons), so that they were blurry with a display scaling greater than 100%, e.g. in warning and error dialogs. `get_std_icon` (and thus `get_icon` for standard icon names, e.g. `ButtonItem(..., "MessageBoxInformation")`) now returns sharp SVG icons for `SP_DirOpenIcon`, `SP_DirClosedIcon`, `SP_DirIcon`, `SP_BrowserReload`, `SP_MessageBoxInformation`, `SP_MessageBoxWarning` and `SP_MessageBoxCritical` (see `guidata.qthelpers.STD_ICON_REPLACEMENTS`); `get_std_icon(name, native=True)` returns the platform icon (fixes [Issue #137](https://github.com/PlotPyStack/guidata/issues/137)).

## guidata Version 3.17.0 ##

* Python 3.10 or later is now required. Python 3.9 users must keep an earlier compatible release.

✨ New features:

* **`get_pixmap` — sharp images with display scaling** — the new `guidata.configtools.get_pixmap` function loads an image as a pixmap at the resolution of the display: when the display scaling is greater than 100% (e.g. 125%, 150%), the high-resolution variants of the image following Qt's `@Nx` naming convention (e.g. `logo@2x.png` next to `logo.png`) are used, so that the image remains sharp instead of being upscaled. `get_image_label` (and thus `get_image_layout`) now relies on it.

🛠 Bug fixes:

* **Text not scaled with display scaling on Windows (Qt5)** — with a Windows display scaling greater than 100% (e.g. 125%), the text of most widgets (labels, buttons, data set editors, ...) kept the size it has at 100%, while menus and status bars were scaled, because Qt5 derives its default font from a legacy system font which ignores the display scaling. Applications created with `guidata.qapplication` (or `qt_app_context`) now use the message font of the system as default font (typically "Segoe UI", 9pt), like with Qt6: the text follows the display scaling and the Windows text size setting.
* **Application startup blocked by a corrupted translation file** — when a `.mo` translation catalog was corrupted or unreadable (e.g. truncated during installation), importing guidata failed with an error such as `OSError: Bad magic number`. The same applied to any application relying on `guidata.configtools.get_translation`, like PlotPy, Sigima or DataLab, so the application could not start at all. The interface now falls back to English, and a `RuntimeWarning` identifies the faulty catalog (fixes [Issue #119](https://github.com/PlotPyStack/guidata/issues/119)).
* **Error when editing a dictionary field in a JSON Schema based form** — in a form generated with `guidata.dataset.dataset_to_schema` (e.g. in a web frontend), editing a `DictItem` field failed with `TypeError: DictItem.__dictedit() missing 1 required positional argument: 'parent'`: the button opening the dictionary editor in the Qt interface was handled as a callback updating the other fields. `DictItem` fields are no longer flagged with `x-guidata-has-callback`, and `resolve_dataset_callbacks` returns an empty mapping for them (fixes [Issue #123](https://github.com/PlotPyStack/guidata/issues/123)).
* **Date/time callback never called** — the `display` callback of a `DateTimeItem` was never called when the date or time was changed in a dataset editor, so that the values computed from it were not updated. The callback is now called on each change, with the new value of the item (a `datetime.datetime` object), like for the other items (fixes [Issue #123](https://github.com/PlotPyStack/guidata/issues/123)).
* **Date callback received a Qt object** — the `display` callback of a `DateItem` received a Qt `QDateTime` object, whose type depends on the Qt binding (PyQt5, PyQt6 or PySide6), instead of the value of the item. It now receives the new value of the item (a `datetime.date` object), like the other items. Callbacks relying on the previous `QDateTime` argument must be updated (fixes [Issue #126](https://github.com/PlotPyStack/guidata/issues/126)).
* **Plain-text "about" information** — `guidata.widgets.about.about(html=False)` (and `AboutInfo.about(html=False)`) failed with `UnboundLocalError` instead of returning the information about the package as plain text (fixes [Issue #123](https://github.com/PlotPyStack/guidata/issues/123)).
* **French translations of the DataFrame editor** — when entering a number format not starting with `%`, the French error message stated the opposite of the actual rule ("must not start with '%'"), and the title of the export dialog box was shown in English. Both are now correctly translated (fixes [Issue #123](https://github.com/PlotPyStack/guidata/issues/123)).

ℹ️ Other changes:

* **Documentation** — `guidata.dataset.resolve_dataset_active`, which evaluates the active state of the items of a dataset for JSON Schema based frontends, is now documented in the API reference.
